# 协程基础知识

> 日期：2026-06-11
> 阶段：协程预热 — 从概念过渡到设计，为 Fiber/Scheduler 实现打基础

## 1. 两个核心操作：Resume 和 Yield

协程的所有控制流归结为两个原语：

```
     调用者                         协程
       │                             │
       ├── resume() ──────────────→  │  从上次 yield 点或入口处开始执行
       │                             │
       │                             │  ... 执行中 ...
       │                             │
       │  ←────────────── yield() ── ├  暂停，保存当前状态，返回调用者
       │                             │
       ├── resume() ──────────────→  │  从上次 yield 点继续执行
       │                             │
```

| 操作 | 语义 | 对应 ucontext API |
|------|------|-------------------|
| **resume** | 保存当前上下文，恢复目标协程上下文 | `swapcontext(&caller, &coroutine)` |
| **yield** | 保存协程上下文，恢复调用者上下文 | `swapcontext(&coroutine, &caller)` |

关键点：**resume 和 yield 在实现上是同一个 swapcontext**，区别只在于方向。从调用者视角是 resume，从协程视角是 yield。

## 2. 什么是协程，如何实现暂停和恢复

**协程 = 一段可以暂停和恢复执行的函数**。普通函数只能从头跑到尾 return，return 后所有局部状态消失。协程可以在中间 yield，下次 resume 从 yield 点继续，局部变量完好。

暂停和恢复的底层实现就是**保存和恢复 CPU 寄存器 + 栈**：

```
暂停（yield）时做的事情：
  1. 保存当前寄存器到一块内存（uc_mcontext）
  2. 从另一块内存恢复目标协程的寄存器
  3. CPU 自动"跳"到目标协程上次停下的位置

恢复（resume）时做的事情：
  1. 同上，只是方向反了
```

ucontext 用 `swapcontext(oucp, ucp)` 一步完成：保存到 `oucp`，从 `ucp` 恢复。这就是为什么 swapcontext 在 Fiber::swapIn/swapOut 中扮演核心角色。

## 3. 协程分类

### 3.1 对称协程 vs 非对称协程

| | 对称协程 | 非对称协程 |
|---|---|---|
| 行为 | 所有协程平等，互相切换，无调用者/被调用者之分 | 有明确的调用者-被调用者层级，被调用者只能 yield 回调用者 |
| 写法 | `transfer_to(other)` | 调用者 `resume(fiber)`，协程内 `yield()` |
| 控制流 | 图状，A→B→C→A，需要自己管理 | 树状，调用者永远在最外层 |
| 代表 | Lua coroutine, Boost.Coroutine (deprecated) | Python generator, JavaScript async/await, sylar Fiber |
| 适用场景 | 复杂的协程协作（管道、状态机） | 简单清晰，调用者统一调度 |

netlib 选择**非对称协程**。调用者是 Scheduler，被调度者是 Fiber。Fiber 只需要知道"切回调度器"，不需要知道其他 Fiber。

### 3.2 有栈协程 vs 无栈协程

| | 有栈协程（Stackful） | 无栈协程（Stackless） |
|---|---|---|
| 栈 | 独立栈空间（malloc，如 128KB） | 使用调用者的栈（或编译器生成的帧，在堆上分段） |
| 挂起点 | 调用栈任意深度 | 仅顶层函数体（`co_await` / `yield`） |
| 栈切换 | 切换栈指针 | 不切换栈，只切换"执行到哪了"的状态 |
| 内存 | 每个协程独立分配 | 和普通函数对象差不多 |
| 实现 | ucontext / boost.context / 手写汇编 | 编译器代码生成（状态机变换） |
| 代表 | sylar, libco, goroutine(go 1.22 前混合) | C++20 coroutine, Rust async, JS async/await |
| 入侵性 | ✅ 业务代码无感知 | ❌ 函数签名要加 `co_await`，有"传染性" |
| 系统调用劫持 | ✅ 可在 read/write 等深处 swapOut | ❌ 必须显式 co_await |

netlib 选择**有栈协程**。核心原因：我们想做 Hook 系统调用，在 `read()` 里遇到 EAGAIN 时自动 yield——这要求协程能在任意调用深度挂起，无栈协程做不到。

### 3.3 有栈协程的进一步细分：独立栈 vs 共享栈

| | 独立栈 | 共享栈 |
|---|---|---|
| 做法 | 每个协程 malloc 一块固定大小栈 | 运行时维护一块大栈，切换时 memcpy 进出 |
| 切换开销 | swapcontext（保存/恢复寄存器） | swapcontext + memcpy（拷贝栈内容） |
| 内存占用 | 每个协程 × 128KB（1000 个 = 128MB） | 一份栈（如 1MB）+ 每个协程 save buffer |
| 溢出风险 | 固定大小，超了就 SIGSEGV | 可以动态扩容，更灵活 |
| 代表 | sylar, muduo | libco（腾讯） |

netlib 选择**独立栈**。共享栈虽然省内存，但 memcpy 每次切换都有额外开销，代码更复杂。独立栈的 128KB × N 内存在学习/中小规模场景完全可接受。

## 4. 协程的优缺点

**优点：**

- **同步写法，异步性能**：`data = read(fd, buf, n)` 看起来是阻塞调用，实际上在 IO 等待时自动切走，性能接近事件驱动
- **避免回调地狱**：一个协程函数写完整个请求处理逻辑，不用拆成 on_read / on_write / on_close 回调链
- **轻量级**：创建/切换比线程快约百倍，`makecontext` + `swapcontext` 纯用户态操作
- **可控调度**：协作式 yield，不需要锁保护协程间的临界区（单线程内），不存在竞态条件
- **栈隔离**：每个协程独立栈，即使某一协程栈有 bug 也不会破坏其他协程

**缺点：**

- **内存：** 10000 个协程 = 1.28GB，纯内存并发受限于栈大小
- **协作式不可抢占：** 如果协程不 yield（死循环、长计算），其他协程全部饿死
- **栈溢出无优雅处理：** 固定栈溢出就是 SIGSEGV，无自动扩容
- **调试困难：** gdb 对 ucontext 切换的调用栈追踪不友好
- **不是线程替代：** CPU 密集型仍需线程并行，协程只解决 IO 等待的调度效率

## 5. 协程 vs 线程 vs 回调

| | 线程(thread) | 协程（ucontext） | 回调（Reactor） |
|---|---|---|---|
| 触发 | 时钟中断 / 系统调用（抢占式） | 用户代码主动 yield（协作式） | 事件循环通知 |
| 特权级 | 用户态 ↔ 内核态 | 纯用户态 | 纯用户态 |
| 切换开销 | ~1-10 μs（含内核调度） | ~几十 ns（swapcontext 虽含 sigmask 系统调用，但仍快一个数量级以上） | 函数调用级 |
| 栈 | 内核栈 + 用户栈（固定 8MB） | 自定义独立栈（128KB） | 复用线程栈 |
| 并发规模 | 数百到数千 | 数千到数万 | 数万 |
| 代码风格 | 同步，最自然 | 同步写法 | 回调链（拆散逻辑） |
| 适用场景 | CPU 密集型 / 需要抢占 | IO 密集型，想用同步写法 | 性能极致、逻辑简单 |

**协程不是线程的替代，而是回调的替代。** CPU 密集型（计算、加解密）仍要交给线程池。协程的价值在于：让 IO 密集型代码（网络服务）以同步风格编写，同时达到接近回调方案的并发性能。

## 6. 调度模型：N:M

后续 Scheduler 的目标：

```
     M 个 Fiber（协程）
    ┌─┬─┬─┬─┬─┬─┬─┬─┐
    │f│f│f│f│f│f│f│f│
    └┬┴┬┴┬┴┬┴┬┴┬┴┬┴┬┘
     │ │ │ │ │ │ │ │
    ┌┴─┴─┴─┴─┴─┴─┴─┴┐     调度器（就绪队列 + 互斥锁）
    └┬─┬─┬─┬─┬───────┘
     │ │ │ │ │
    ┌┴─┴─┴─┴─┴┐           N 个线程（Scheduler 线程池）
    │t│t│t│t│t│
    └─┴─┴─┴─┴─┘

    任何线程可以执行任何 Fiber（可选线程绑定）
    互斥锁保护就绪队列
    epoll_wait 触发 IO 就绪 → Fiber 入队 → 空闲线程取走执行
```

N 远小于 M（如 N=4, M=5000）。协程在 IO 等待时不在队列中，不占 CPU。io_uring 或 epoll 通知 IO 就绪后，协程重新入队等待调度。这就是协程和线程的协作关系——一个负责"等待"，一个负责"计算"。
